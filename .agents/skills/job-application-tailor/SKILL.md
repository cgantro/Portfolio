# 채용공고 맞춤형 지원서류 튜닝

Codex에서 사용한다. 이 파일과 선택한 모드의 참고 문서를 따른다.

## 모드와 입력

사용자가 명시한 작업과 산출물을 모드 자동 선택보다 우선한다. 요청받은 서류만 처리한다.

- **모드 A — 공고 맞춤형 작성:** 공고 내용과 경험 근거가 필수다. 이력서, 경력기술서 또는
  사용자가 확인한 경험 기록을 사용한다. 기존 자기소개서와 포트폴리오는 선택 자료이며
  없어도 요청한 서류를 신규 작성할 수 있다.
- **모드 B — 공고 비교:** 공고 2개 이상과 사용자 경력 프로필이 필수다. 희망 직무·근무조건과
  가중치는 선택 입력이다. 비교·순위를 요청했을 때 적용한다. 여러 회사의 서류 작성을
  요청했다면 회사별 모드 A를 수행한다. 프로필을 확보하지 못하면 공고 요약만 제공한다.
- **모드 C — GitHub 정리:** 대상 계정과 Public/Private/둘 다의 조회 범위가 필요하다.
  계정 미지정 시 로컬 인증 계정을 기본값으로 사용하고 결과에 명시한다. 공개 범위가
  미지정이면 질문한다. 조직은 명시된 조직만 포함하며 기본은 개인 계정 소유 저장소다.

공고 URL에 접근할 수 없으면 원문 텍스트를 요청한다. 새로운 선택이나 미확인 사실이 결과를
바꾸는 경우에만 질문한다. 이미 제공한 계정, 조회 범위, 포함 저장소와 후속 작업은 재확인하지
않는다. 모드 C의 신규 후보는 포함 대상을 확인하고, 승인된 경험만 A/B의 입력으로 사용한다.

## 공통 원칙

1. **확인된 사실을 유지한다.** 없는 경력, 기술, 수치, 기간, 자격, 직함과 역할을 만들지 않는다.
   팀 성과를 개인 단독 성과로 바꾸지 않으며 직접 실행과 의사결정의 주체를 구분한다.
   지시받아 실제 수행한 업무도 경험으로 서술할 수 있다.
2. **자기소개서는 사실 범위 안에서 표현을 강화한다.** 경험의 배치, 행동 동사와 설명의
   선명도를 개선한다. `주도`, `총괄`, `전문가` 등은 해당 책임과 숙련도의 근거가 있어야 한다.
   면접에서 설명할 수 있다는 조건은 사실 확인을 대신하지 않는다. 질문과 무관한 불리한
   세부사항은 줄일 수 있지만 질문이 요구한 사실을 숨겨 오해를 유도하지 않는다.
   자기소개서의 수치를 반올림하거나 범위로 쓸 때는 의미·정밀도를 보존하고 `약` 등으로
   표시한다. 이력서, 포트폴리오, GitHub 초안과 채점에서는 확인된 수치를 그대로 사용한다.
3. **근거와 확인 상태를 추적한다.** 주요 역할, 기간과 수치는 근거 파일의 위치 또는 사용자
   확인 내용과 연결한다. 충돌하는 자료는 임의로 합치지 않는다. 확인된 사실, 추정과 미확인을
   검토 메모에서 구분한다. 중요한 미확인은 질문하고 답변 전에는 보수적으로 작성한다.
4. **원본과 이전 산출물을 보존한다.** 아래 저장 규칙에 따라 새 버전으로 저장한다.
5. **언어와 문체를 유지한다.** 원문의 어조를 살리되 어색한 반복과 번역투까지 보존하지 않는다.
   짧은 나열은 쉼표나 조사로 연결한다. 마지막 항목의 `그리고`는 의무가 아니며, 슬래시는
   선택·병렬 관계가 명확할 때만 사용한다. `·`는 원본 양식이나 짧은 메타정보에서 필요한
   경우로 제한한다. 근거·상태가 붙는 항목은 목록이나 표를 사용할 수 있다.
6. **조회 허용과 공개 가능 범위를 구분한다.** GitHub는 로컬 인증 세션으로 읽고 토큰을
   코드·문서에 적지 않는다. 비공개 자료를 스킬 저장소에 보관하거나 별도 외부 서비스에
   업로드하지 않는다. 회사·팀 소유 여부와 공개 가능한 내용을 확인한 뒤 지원서에 포함한다.

## 자기소개서 작성 원칙

### 질문별 구성

- 작성 전에 문항과 하위 질문을 분리하고 각각에 답과 근거를 배치한다.
- 첫 문장은 질문에 대한 답 또는 핵심 역량을 직접 전달한다.
- 지원 동기는 선택 이유와 경험의 연결, 문제 해결·협업은 상황·역할·행동·결과,
  실패 경험은 원인·대응·배운 점, 입사 후 계획은 목표·실행 방법을 중심으로 구성한다.
  이는 예시이며 질문이 요구한 내용이 우선이다.
- 지원서 전체에서 우선할 공고 요구사항 2~3개를 고른다. 문항별 경험 수는 질문과 분량에
  맞추고 짧은 답변은 핵심 경험 하나를 우선한다. 모든 문항에 여러 경험을 강제하지 않는다.
- 입사 후 기여와 별도 마무리는 질문에 필요할 때만 넣는다. 도입 뒤에는 주장의 반복보다
  본인의 역할, 판단과 행동을 보여주는 근거를 제시한다.

### 도입과 표현

- 비유는 선택 사항이다. 사용할 때는 첫 문장 자체가 질문에 답하고 실제 경험으로 증명되어야
  한다. 비유를 설명하느라 같은 주장을 반복하게 되면 평이한 도입으로 바꾼다.
- 특정 인물·작품의 표현이나 사용자가 제시한 예문을 복사하지 않는다. 사용자의 경험에서
  표현을 만들며, 인상적인 문장을 위해 사실과 책임 범위를 확대하지 않는다.
- 공고의 문화·가치관 키워드는 확인된 범위만 반영한다. 없는 키워드를 채우거나 여러 번
  반복하는 것으로 적합성을 증명하지 않는다. 실제 행동으로 연결한다.

### 반복 점검과 교정

- 문항 질문과 메타정보를 제외한 답변 본문을 문항별로 검사한다. 동일 핵심어가 **5회 이상이면
  반드시 재검토**한다. 이는 자동 삭제 상한이 아니다. 횟수가 적어도 인접 문장에 반복되는
  단어, `~을 통해` 같은 구절과 새 정보 없이 되풀이하는 주장을 점검한다.
- 영문 대소문자와 조사 부착은 같은 핵심어로 집계한다(`AI`, `ai`, `AI를`). 다른 영단어
  내부의 `ai`는 세지 않는다. 띄어쓰기·하이픈 차이는 같은 용어인 경우만 정규화한다.
  `AI 기반`과 `생성형 AI`의 AI 등장도 집계하되 개념 전체가 동일하다고 단정하지 않는다.
- 동의어로 감춰진 의미 반복도 읽어 확인한다. `AI`를 `인공지능`으로 바꾼 것만으로 해결됐다고
  판단하지 않는다. 문항 사이에는 동일 문장과 주장 재사용을 점검하되 독립된 답변에서
  필요한 기술명이 다시 등장하는 것은 허용한다.
- 교정 순서: 중복 문장 삭제·통합 → 불필요한 수식어·주어 생략 → 확인된 행동과 대상으로
  구체화 → 의미가 정확한 대체 표현. 원본에 없는 구현 방식이나 성과를 추가하지 않는다.
- 대상 구분이나 정확성이 훼손될 때만 반복을 유지하고 검토 메모에 이유를 남긴다. 기술명이라는
  이유만으로 일괄 제외하지 않는다. 교정 후 의미, 필수 기술명과 질문에 대한 답을 다시 확인한다.

### 분량과 초안 상태

- 공고의 글자/바이트 제한과 공백·줄바꿈·제목 포함 여부를 확인하고, 최종 교정된 답변을
  해당 방식으로 실제 계산한다. 바이트 제한이면 인코딩도 확인한다. 기준이 불명확하면
  사용한 계산 방식을 보고하고 제출 시스템과의 일치 여부는 미검증으로 남긴다.
- 미확인 사실이 필요한 문항은 초안으로 표시한다. 확인 질문, 근거와 `본인 확인 필요` 표시는
  제출 본문 밖의 검토 메모에 둔다. 확인 전에는 제출용 최종본이라고 보고하지 않는다.

## 모드 A — 작성 절차

1. **공고 분석:** 회사·팀·직무, 필수 조건, 우대사항, 업무, 기술명, 명시된 문화 키워드와
   제출 제약을 추출한다. 복합 요건의 AND/OR 관계를 보존하고 추정한 채용 배경을 사실로 쓰지 않는다.
2. **매칭:** 요구사항별 근거를 연결하고 충족, 부분 충족, 미충족과 미확인을 구분한다.
   미기재를 곧바로 경험 없음으로 판단하지 않는다. 중요한 미확인만 질문한다.
3. **이력서:** 요청한 경우 관련 경험을 앞으로 배치하고 기존 수치를 살린다. 공고의 정확한
   기술·도구 명칭은 사실과 일치할 때 사용한다. 원본 양식과 섹션을 가능한 범위에서 유지한다.
4. **자기소개서:** 요청한 경우 위 작성 원칙으로 질문별 초안을 작성하고 반복 교정과 분량
   재계산을 수행한다. 본인 수행 범위와 팀 성과를 원본에 대조한다.
5. **포트폴리오:** 요청한 경우 관련 프로젝트, 의사결정과 성과의 우선순위를 조정한다.
   관련성이 낮은 경험은 삭제보다 우선순위 하향을 제안하고 원본은 보존한다.
6. **저장:** 아래 공통 저장 규칙을 적용한다.
7. **검수:** `reference/checklist.md`를 읽고 요청한 산출물에 해당하는 항목을 확인한다.
   충족 근거, 질문별 답변, 사실성, 반복, 최종 분량, 원본 보존과 초안 상태를 검토한다.

출력: 공고 요약, 매칭과 부족한 요건, 변경 파일, 핵심 변경 내용과 미확인·미검증 항목.
작은 수정은 변경 규모에 맞게 간결하게 보고한다. 메타정보와 확인 질문을 제출 본문에 섞지 않는다.

## 모드 B — 비교 절차

1. 공고별 요구사항과 사용자의 실제 경력·희망 조건을 정리한다.
2. 채점 전에 `reference/ranking-criteria.md`를 읽고 상태 구분, 계산식과 등급 규칙을 적용한다.
3. 근거가 부족한 공고는 잠정 범위와 정보 충족률을 표시한다. 지원 필수 조건 미충족은 점수와
   별도 표시하고 강력 추천으로 출력하지 않는다. 평가 근거가 전혀 없으면 점수·순위를 만들지 않는다.
4. 비교표에 점수 또는 범위, 등급·상태, 핵심 근거, 부족한 요건과 가중치를 표시한다.
   겹치는 범위나 근소한 차이는 무리하게 서열화하지 않는다. 많은 공고는 요약과 전체 표를 나눈다.
5. 사용자가 이미 지정한 후속 작성은 이어서 수행한다. 대상 선택이 필요한 경우에만 질문한다.

## 모드 C — GitHub 정리 절차

실행 전에 `reference/github-scan-criteria.md`를 읽는다. GitHub에 쓰기 작업을 하지 않는다.

1. **환경:** `gh --version`, `gh auth status`로 로컬 환경과 인증을 확인한다. 요청 대상의
   읽기 권한으로 접근 가능성을 판단한다. 특정 스코프 문자열이 없다는 이유만으로 실패를
   단정하지 않으며 임의로 권한을 확장하지 않는다.
2. **범위:** 입력에서 받은 계정, 공개 범위와 조직을 적용한다. 신규 후보의 포함 여부와
   공개 가능 범위만 필요한 시점에 확인한다.
3. **목록:** 참고 문서의 범위별 명령으로 수집한다. 조회 한도와 누락 가능성을 보고한다.
   포크 차이·커밋 수를 확인하지 못했다면 추측으로 제외하지 않는다.
4. **조사:** README, 관련 설정·의존성 파일, 릴리스 등의 근거를 확인한다. 언어 통계는 보조
   근거이며 커밋 수 비율을 실제 기여도로 환산하지 않는다. 기여자 한 명만으로 개인 프로젝트라고
   확정하지 않는다. 생성일~마지막 푸시일은 저장소 활동 기간이고 실제 수행 기간은 별도 확인한다.
5. **확정:** 후보와 제외 사유, 저장소 활동 기간, 사용 언어, 커밋 수 비율을 요약한다.
   이미 지정한 저장소는 다시 승인받지 않는다. 새 후보와 미확인 실제 역할·기간·공개 범위를
   함께 질문한다. 공개 가능 여부가 미확인인 정보는 제출용 초안에 포함하지 않는다.
6. **초안:** 확정된 저장소만으로 참고 문서의 Markdown 형식과 저장 규칙을 적용한다.
   README의 프로젝트 성과를 개인 성과로 옮기기 전에 역할을 확인한다. 기술 스택 집계도
   확정된 저장소만 대상으로 한다. 미확인 사실과 호환성은 검토 메모에 표시한다.

출력: 조회 범위·누락, 후보와 판단 근거, 생성 파일, 실제 역할·기간·공개 여부의 미확인 사항,
편집기 호환성 검증 여부. 사용자가 요청한 후속 A/B 작업은 확인된 근거로 이어간다.

## 공통 저장 규칙

- 저장 위치의 문서 규칙을 우선한다. 별도 규칙이 없으면 다음 이름을 사용한다.
  - `이력서_{회사명}_{직무명}_v01.md`
  - `자기소개서_{회사명}_{직무명}_v01.md`
  - `포트폴리오_조정메모_{회사명}_{직무명}_v01.md`
  - `github_프로젝트_초안_{YYYY-MM-DD}_v01.md`
- 저장 전 파일 존재 여부를 확인하고 다음 사용 가능한 버전(`v02`, `v03`)을 선택한다.
  원본, 이전 초안과 제출본을 덮어쓰지 않는다. 파일명에 사용할 회사·직무명에서 경로 구분자는 제거한다.
- 원본 형식을 유지할 수 있으면 해당 확장자를 사용한다. 변환하거나 텍스트 수정안만 제공했다면
  글꼴·시각 양식을 보존했다고 보고하지 않는다. 포트폴리오는 기본적으로 별도 조정 메모를 제공한다.
- 제출 본문과 별도인 버전별 검토 메모에 대상 공고, 원본 경로, 작성일, 주요 변경사항,
  사실 근거, 미확인 항목, 반복 예외와 분량·형식 검증 결과를 남긴다.
- 미확인이 남으면 파일·보고에서 초안임을 명시하고 제출용 최종본으로 분류하지 않는다.
