# Korean Technical Resume
1. Parse JD must-haves, actual work tasks, and length/format requirements. Use a general profile if no JD is supplied.
2. Search actual project and career source material. Track each experience by source path or evidence ID.
3. Select the best experiences for the role. Include purpose, personal contribution, a specific design/debug/implementation decision and verified impact. Do not write shallow stacks-only lists.
4. Do not inflate team achievement into personal ownership. Separate implemented features, planned changes, and unverified claims.
5. Keep metric baselines, sample count, percentiles, units and experimental limitations. Never infer improved latency from increased FPS alone.
6. Write polished professional Korean. Connected sentences and nominalization are acceptable if useful; do not force short prose or colloquial tone.
7. Produce final draft plus evidence map and flagged unknowns in a separate review section.
8. Request an independent resume redteam when meaningful factual risks exist. Do not treat heuristic ATS scores as real hiring predictions.

## Resume fact and ATS checks
- Treat the resume, user-confirmed facts, and cited project evidence as the only sources of candidate claims. Never infer dates, metrics, ownership, team size, technologies, or results; leave a clear placeholder or ask when evidence is missing.
- Keep individual contribution separate from team outcomes. Preserve metric baseline, sample count, units, time window, and measurement conditions.
- Compare job requirements with supported resume evidence and identify genuine gaps. Do not present keyword counts, ATS match percentages, parser behavior, or hiring outcomes as universal scores or predictions.
- Check that headings and document structure are extractable from the actual output format when relevant. Recommend a formatting change only when a real parser or document inspection demonstrates an issue.
