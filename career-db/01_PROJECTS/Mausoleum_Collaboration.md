# Mausoleum — 다중 방 운영 방식 공동 결정과 시스템 통합

> **핵심 경험:** 서버 개발자 두 명이 다중 방 운영 구조를 논의하던 중 단일 UE5 Dedicated Server 방식을 먼저 제안했다. 다른 담당자가 우려한 방별 상태 혼선과 클라이언트 수정 범위를 고려해 팀원들에게 변경 계획을 미리 알리고 구조를 수정했다. 이후 여러 방을 실행해 공간 중첩을 발견하고 방별 배치 간격을 조정했다.

## 1. 상황(S)

- UE5 기반 협동 탈출 게임, 6인 팀 프로젝트.
- 로비에서 방 생성·입장 후 전용 서버에 접속하여 협동 게임을 진행하는 구조.
- 서버 개발자는 본인 포함 2명. 본인은 C++ 로비·UDP 음성 서버 및 UE5 클라이언트 음성 통신 구현에 참여했다.
- 게임 시작 후 방별 플레이어·아이템·이벤트·타이머를 독립적으로 운영하는 방법을 정해야 했다.
- 당시 서버 및 엔진 구조에 익숙하지 않아 두 서버 개발자가 방마다 전용 서버를 실행할지, 하나의 전용 서버에 여러 논리적 방을 둘지 의논했다.

## 2. 문제와 공동 의사결정(T)

- **[사용자 확인]** 본인이 단일 전용 서버 방식을 먼저 제안했다. 동료 개발자와 정보를 비교한 뒤 프로젝트 상황에 단일 서버가 적합하다는 데 의견을 모았다.
- **[사용자 확인]** 상대 개발자는 여러 방의 플레이어·아이템·이벤트·타이머가 섞이는 문제를 걱정했다. 서버뿐 아니라 클라이언트 측 수정도 적지 않았다.
- **[기술적 비교; 당시 사용한 원본 비교표는 미확인]** 방별 UE5 서버 인스턴스 방식은 게임 월드·상태가 자연스럽게 분리되는 반면, 방마다 프로세스 실행, 주소·포트, 시작·종료를 운영해야 한다. 단일 서버 방식은 그 반복 관리 부담을 줄일 여지가 있지만, 게임 상태와 공간을 별도로 분리할 책임이 생긴다.
- **[판단의 프로젝트 적합성]** 서버 개발 인원이 2명인 제한된 팀에서 인스턴스 관리 기능까지 별도로 확대하기보다, 로비에서 이미 사용하던 RoomCode를 게임 상태와 음성 통신으로 이어 방별 분리 구현에 집중하는 방식을 선택했다.
- **주의:** 마지막 두 항목은 프로젝트 구조에 근거한 설명이다. 당시 회의에서 정확히 이 순서·표현으로 비교했다거나 RAM/CPU 절감 수치를 측정했다고 주장하지 않는다.

## 3. 협업 행동(A)

1. **[사용자 확인] 사전 공지:** 다중 방 구조 변경을 시작하기 전에 팀원들에게 작업 계획을 알렸다. 공지 채널·문구·상세 일정은 미확인.
2. **[사용자 확인 + 코드 근거] 초기 구조 변경:** RoomCode를 중심으로 게임별 플레이어와 상태·페이즈를 구분하고, 하나의 서버 월드에 방별 공간을 따로 배치하는 구조를 도입했다. 2026-03-17 대규모 변경에는 Client/Server/Shared 모듈 분리도 포함됐다.
3. **[사용자 확인] 기능 테스트:** 여러 방을 직접 실행하면서 서로 다른 방의 게임 공간이 물리적으로 겹치는 문제를 발견했다.
4. **[코드 근거 + 사용자 확인] 문제 수정:** `RoomWorldOffset.h`의 방별 X축 위치 간격을 늘려 큰 맵이 겹치는 문제를 수정했다. 기록상 2026-03-20에는 간격이 50,000 UE 단위였고, 2026-03-27에 5,000,000으로 확대됐다. 이는 일반적인 부하 시험 수치가 아니라 공간 배치 상수 변경이다.
5. **[코드 근거] 다른 담당자의 후속 작업:** 로비 및 전용 서버 접속, 방별 플레이어 등록·조회, 게임 페이즈 전환 오류 등이 서로 다른 커밋에서 보완됐다. 이 부분은 팀 공동 결과로 구분한다.
6. **[사용자 확인 + 코드 근거] 음성 규칙 요구 수용:** 팀원에게 로비 전체 음성, 생존자 간 거리감쇠·공간음향, 사망자 청취 방식 요청을 받아 음성 정책을 개편했다. 실제 구현된 세부 정책과 최초 요청의 표현은 일치하지 않을 수 있으므로 구분한다.

## 4. 결과(R)와 검증 한계

- **[사용자 확인]** 여러 방을 실행해 발견한 실제 맵 공간 중첩 문제를 수정했다.
- **[코드 확인]** RoomCode를 공유하는 로비·게임 서버·음성 통신 구조, 방별 진행 상태와 공간 오프셋 관리, 후속 접속·페이즈 보완 커밋이 존재한다.
- **[측정 없음]** 서버 프로세스별 메모리·CPU 절감, 최대 동시 방 수, 처리량, 비용 절감률은 입증하지 않았다.
- **[제한]** 해시 기반 방 슬롯 할당에 충돌 가능성이 있으므로 모든 경우의 완전 격리나 서버 규모 확장에 대한 보장으로 과장하지 않는다.
- **[회고]** 변경의 장점을 설명하는 것만큼, 동료가 우려한 방 간 혼선과 다른 담당자의 수정 부담을 설계 조건에 포함하고 사전에 알리는 일이 중요했다.

## 5. 협업 자기소개서 활용 초안 (두괄식 · STAR)

6인 협동 게임 ‘영묘’에서 서버 개발 동료와 다중 방 운영 방식을 결정하고, 팀원에게 변경 계획을 공유한 뒤 방별 게임 환경을 구현·검증했습니다.

로비에서는 방을 만들 수 있었지만, 게임을 시작하면 각 방의 플레이어와 진행 상태를 독립적으로 유지해야 했습니다. 저는 C++ 로비·음성 서버와 UE5 음성 통신을 맡았고, 다른 서버 개발자와 함께 방마다 전용 서버를 실행할지 논의했습니다.

제가 먼저 단일 전용 서버 방식을 제안했습니다. 방마다 UE5 서버를 띄우면 게임 상태를 분리하기는 쉽지만, 같은 게임 월드를 실행하는 프로세스가 방 수만큼 늘고 서버 시작·종료와 접속 주소까지 관리해야 했습니다. 반면 로비에서 이미 사용하던 RoomCode를 활용하면 하나의 서버에서 방을 구분할 수 있었습니다. 서버 담당자가 두 명인 상황에서 별도의 서버 인스턴스 관리 기능까지 만드는 것보다, 방별 상태 분리에 개발을 집중하는 편이 적합하다고 판단했습니다. 동료는 아이템·이벤트·타이머가 방 사이에 섞일 가능성을 우려했고, 저희는 이를 반드시 해결해야 할 조건으로 두고 단일 서버 방식에 합의했습니다.

클라이언트와 게임 진행 코드에도 수정이 필요해 먼저 팀원들에게 구조 변경 계획을 알렸습니다. 이후 RoomCode에 따라 플레이어와 진행 상태를 구분하고, 방별 맵을 다른 좌표에 배치하는 1차 작업을 진행했습니다. 여러 방을 실제로 실행하자 맵이 물리적으로 겹치는 문제가 드러났고, 맵 크기에 비해 좁았던 배치 간격을 넓혀 해결했습니다. 다른 담당자들도 게임 접속과 방별 플레이어·단계 전환 기능을 보완했습니다.

이 경험을 통해 설계 선택의 이점뿐 아니라 동료가 우려한 위험과 다른 담당자의 수정 범위까지 함께 다뤄야 기능을 통합할 수 있음을 배웠습니다.

> **검증 주의:** 위 자소서 초안의 '프로세스 시작·종료와 접속 주소 관리 부담'은 구조상 타당한 비교 근거이나, 당시 회의에서 실제로 언급한 구체 항목은 별도 회의록이 없어 미확인이다. 면접 전 본인의 기억과 일치하는지 확인해야 한다.
