# Reactive Resume v6

The repository provides a REST connector and an MCP configuration example. It does not contain an account token, a fabricated resume, or an account export. Offline validation, JSON Resume preparation, and portfolio PDF builds work without Reactive Resume.

Configure `REACTIVE_RESUME_API_URL` and `REACTIVE_RESUME_API_KEY` in the process environment. The URL is an HTTPS instance origin, or the instance's `/api/openapi` base. HTTP is allowed for loopback self-hosting. `REACTIVE_RESUME_ID` selects an existing owned resume for export. Credentials are never accepted through command arguments, copied to a journal, or printed in errors. `.env.example` describes the optional timeout and journal settings; copy it outside tracked files if using a local environment loader.

`npm run resume:prepare` produces JSON Resume and its loss report without a network call. `npm run resume:export` downloads an existing account resume selected by `REACTIVE_RESUME_ID`; it exits with an error when configuration is missing, the response is not a PDF, or the resulting PDF cannot be parsed. A temporary download never replaces a valid artifact until validation passes. Export never creates or imports an account resume.

The library `importJsonResume` is an explicit write operation for a future authorized caller. It validates input, computes a canonical content fingerprint, records a non-secret journal before dispatch, and tags successfully imported records with that fingerprint. Repeated successful imports reuse their existing resource. The v6 service does **not** implement `Idempotency-Key`; the connector never blindly retries imports. On timeout, network failure, invalid success JSON, or server error it lists and reads candidate resources before returning success or an `AMBIGUOUS_WRITE` error. A pending journal continues reconciliation on a later invocation. If reconciliation cannot prove which resource was created, inspect the account and resolve the journal manually before any new import. Eventual consistency or concurrent identical imports can leave an ambiguous state.

Reads have bounded timeouts and one retry for network/transient server failure. API metadata, full resume essentials, error codes, and binary PDF signatures are validated. Response bodies and API keys are excluded from error messages. Metadata writes re-fetch after an uncertain response and do not automatically repeat the write.

For MCP, add a remote Streamable HTTP server using the instance URL followed by `/mcp`, and sign in through the client's OAuth flow. `mcp.example.toml` is a configuration reference, not an installed connection. The environment header map is optional for clients that support it. Keep credentials in the environment or the client's private credential store. Discover the live tool catalog with `tools/list`, list and read existing documents first, and reconcile every ambiguous write before retrying. PDF tool links are temporary; download and verify actual bytes before recording an export as successful.

Official contracts: [v6 API guide](https://github.com/reactive-resume/reactive-resume/blob/main/docs/guides/using-the-api.mdx), [MCP guide](https://github.com/reactive-resume/reactive-resume/blob/main/docs/guides/using-the-mcp-server.mdx), and the installed instance's `/api/openapi/spec.json`. Endpoint details were checked against the public v6 OpenAPI specification on 2026-10-15. Authentication and account state must be checked again in the target instance.

## ResumeData mapping and job variants

Imports take an exclusive local lock per content fingerprint. Concurrent callers sharing a state directory fail with `IMPORT_BUSY` instead of sending duplicate creates. A process crash can leave a lock; inspect the account and pending journal before removing a stale lock. Separate machines must share a coordination store or serialize imports externally.

`toReactiveResumeImport(careerData, editionId)` returns a validated JSON Resume, explicit mapping losses, the edition ID, and a distinct document name. The v6 `/resumes/file-imports` endpoint's `JSON_RESUME` importer performs the schema-aware conversion into its current `ResumeData`, including structured dates. The connector then reads and validates the created resource's ID, metadata, `data.basics`, and `data.sections.projects` before reporting success. This is an API-based adapter; it does not manufacture an incomplete local `ResumeData` object or pretend that a JSON file is an account document.

After explicit authorization for account creation, an application can pass each prepared plan to `client.importJsonResume(plan.resume, { name: plan.name })`. The three required editions have distinct headlines, project ordering and skill focus, so their content fingerprints and private account variants are distinct. Reusing identical content is idempotent at the client/journal layer. Changed source content creates another private variant with a new fingerprint; the connector does not overwrite a user's edited resume. For this initial delivery, the `cpp-software`, `simulation`, and `video-software` drafts were explicitly imported through the connected MCP on 2026-10-15 and read back; all remain private. The repository stores neither account IDs nor credentials. `resume:export` reads an existing environment-selected document and never imports one implicitly.
