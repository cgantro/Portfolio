### A1. 한국어 문체 규칙 — 최우선

- 고용용 기술 포트폴리오에 자연스러운 **담백한 한국어 서술체(주로 `~했습니다`, `~구현했습니다`, `~확인했습니다`)**를 사용한다. 필요하면 동사를 압축한 명사형 제목을 쓴다.
- 본인의 개발 행위가 문장의 중심이어야 한다. `~을 설계했다`, `~을 직접 측정했다`, `~을 분리했다`, `~을 비교했다`와 같이 **주체·대상·행동이 구체적**이어야 한다.
- 모든 문장에 `저는`을 붙이지 말고, 그렇다고 본인 담당인지 전체 팀 결과인지 모호하게 생략하지도 말 것. 프로젝트 개요는 전체 시스템, 담당 역할/구현은 본인 작업으로 구분한다.
- `어디까지 확인했나`, `무엇을 확인했나`, `시스템은 어떻게 움직이나`, `직접 구현한 내용`, `아래에서 살펴봅니다`, `위 수치`, `아래 상세 사례`, `기술력을 보여줍니다` 같은 질문형·메타 설명형·강의체 제목/문장 사용 금지.
- `기록되어 있습니다`, `공개 문서에서 확인됩니다`, `자료에서 찾을 수 없습니다`, `이 페이지에는`, `본 포트폴리오는`, `사용자의 경험을`, `제공된 설계안` 등 **감사/검수 보고서의 흔적**을 사용자에게 보이는 본문에서 제거한다. 증거가 부족한 내용은 보류하거나 별도 검증 조건 한 줄로 제한한다.
- `지직거리거나`, `일을 이어갔습니다` 등 구어체는 실제 현상 표현에만 사용하고, 설명 전체를 지나치게 대화식으로 쓰지 않는다. `Main Thread`, `Worker`와 `주 스레드`, `작업 스레드` 표기를 한 프로젝트 안에서 통일한다.
- 독자가 익히 알고 있을 가능성이 높은 TCP/UDP, MQTT, Opus, FPS, FK/IK, PBO, STOMP, Jolt 등의 용어마다 `(메시지 발행·구독 프로토콜)`처럼 사전식 괄호를 넣지 않는다. 낯선 용어는 문맥으로 설명하거나 필요한 경우 첫 등장에만 설명한다.
- 문단을 `A했습니다. B했습니다. C했습니다.`의 단조로운 나열로 만들지 않는다. 중요 기능은 **구현 목적 → 처리 방식 → 중요한 결정** 순서로 문장 관계를 명확히 한다.
- 확인·검증·기록이라는 동사를 문단마다 반복하지 않는다. `구현했습니다`만 연속해 사용하는 것도 피한다.
- `안정적으로`, `최적화했습니다`, `신뢰성을 확보했습니다`, `성능을 크게 개선했습니다`처럼 조건 없는 평가를 없애고 어떤 오류·지연·구조를 다뤘는지 기술한다.
- 짧게 쓰되 중요한 구체성을 지우지 않는다. 기초 용어 정의나 불필요한 수식보다 `무엇을/왜/어떻게`를 우선한다.
- 발표나 면접에서 스스로 소리 내어 읽어도 어색하지 않아야 한다. 문장이 기계적이거나 어색하면 **섹션 형식을 바꾸는 선택**도 허용한다. 모든 카드를 채울 필요가 없다.

### A2. 대표적인 문장 교정 규칙

| 현재/문제형 | 바꿀 방향/예시 |
|---|---|
| `성능이 떨어지면 처리 시간을 재고, 실제 병목을 찾아 고칩니다.` | `영상 스트리밍 과정의 처리 시간을 측정하고, 병목 구간을 분리해 구조를 개선했습니다.` |
| `무엇을 확인했나` | `주요 성과` / `측정 결과` |
| `어디까지 확인했나` | `검증 결과` / 필요 시 `측정 조건 및 한계` |
| `시스템은 어떻게 움직이나` | `시스템 아키텍처` |
| `실측 속도는 아래 상세 사례에 정리했습니다.` | 삭제. 해당 내용에서 곧바로 측정·보정 행동을 적음 |
| `Java 기반 보조 사례로 ... 경험을 보여줍니다.` | 삭제. Java 프로젝트 자체의 역할과 기술 난제를 설명 |
| `부하 시험은 문제 해결이 아니라 검증으로 분리했습니다.` | 삭제. 편집 이력을 독자에게 공개하지 않음 |
| `프로젝트 기록에는 정상 재생 결과가 기재되어 있습니다.` | `포커스 복귀 시 오래된 음성이 이어서 재생되지 않도록 수정했습니다.` 단, 검증 사실만 기재 |
| `동작 원리를 반영하도록 구성했습니다.` | 정확히 어떤 계산·데이터·인터페이스를 사용했는지 서술 |
| `검증 오차를 확대 해석하지 않습니다.` | 필요할 경우 `실측 보정 전후의 정량 오차는 측정하지 않았습니다.` 한 번만 |
| `코드는 실제 소스가 아닌 의사코드입니다` 반복 | 의사코드는 특별한 경우만. 원본 코드면 경로·라인·생략 여부를 명시 |
| `현재 연결할 수 있는 공개 저장소가 없습니다.` | 빈 영역 삭제. 공개 링크가 없으면 렌더링하지 않음 |

### A3. 원칙 — 정보 밀도와 섹션 위계

- 첫 화면 5~10초에 `어떤 개발자인가 → 대표 기술 영역 → 프로젝트 목록`을 알 수 있게 한다.
- 각 프로젝트 카드에서 `무엇을 만든 프로젝트인가`와 `본인이 무엇을 담당했나`를 우선 확인할 수 있어야 한다. **기술 스택 5개 나열과 수치만 보여주는 카드는 부족하다.**
- 프로젝트 상세 페이지의 개요(전체 제품 설명), 담당(본인 범위), 구현(기술적 수행 내용), 트러블슈팅(문제 해결), 검증(측정 방식/범위)을 분리한다. 겹치는 내용은 가장 적합한 단 한 곳에 배치한다.
- **프로젝트별로 구성 순서와 섹션 존재 여부가 달라도 된다.** 그 이유가 정보 위계로 설명돼야 한다. `sectionOrder` 사용 가능하나 데이터에 없는 섹션을 더미로 채우지 말 것.
- 트러블슈팅 사례는 **현상이 실제 발생/재현됐는지**와 **설계상 위험을 예방한 것인지** 구분한다. 설계 선택을 관측된 장애로 꾸미지 않는다.
- 기술 사양·설정값은 성과 숫자가 아니다. 수치 카드에는 실제 비교 가능하고 읽는 사람에게 의미가 있는 성과만 넣는다.
- 수치·측정 조건·한계는 필요한 위치에서 한 번만 제시한다. 사례 카드의 `한계`와 `검증`에서 같은 문장을 중복하지 않는다.
- 코드/의사코드는 옵션. 원본 코드가 없는 프로젝트에 임의 코드를 만드는 것이 목적이 아니다.
- 모바일 360/390/768px, 데스크톱 1280/1440px 기준으로 제목, 줄바꿈, 카드 정렬, 데모가 무너지지 않는지 시각 검증한다.

## B. 파일별 정확한 수정 대상 — `8ede25f` 기준

### B1. 첫 화면/전역

1. `src/pages/HomePage.jsx`
   - 인트로 `6축 로봇팔의 기구학과 경로 계획부터...`, `성능이 떨어지면...`은 추상적이고 일상 구어체. 실제 작업에서 추출한 **직무 정체성 + 차별 경험 2개**로 교체한다.
   - `성능 측정과 검증`은 넓은 기술 역량이지 별도의 개발 도메인이 아닐 수 있음. 로봇 시뮬레이션 / C++ 시스템·그래픽스 / 실시간 통신·영상·음성 처리 같은 실제 경험 기반 축으로 재정리하되 키워드 나열을 늘리지 않는다.
   - 홈 프로젝트 카드의 `summary`는 팀 프로젝트 전체 개요를 전달하고, **`내 역할`을 명시하는 별도 1줄 필드를 추가**한다. 상세 페이지 `role`과 별도로 카드용 짧은 역할(`cardRole`)을 두어 긴 텍스트를 잘라 쓰지 않는다.
   - `homeHighlight`는 대표 메시지일 때만 표시한다. GraspLink의 `FK · IK · MoveJ...`와 태그 영역이 중복되지 않도록 역할/특징 하나만 강조한다. 성과가 없는 경우 억지로 수치나 스펙을 만들지 않는다.
   - `주요 프로젝트 · 2024–2026`의 시작연도가 실제 게시된 대표 프로젝트와 일치하는지 확인한다. 4개 대표 프로젝트 모두 2025/2026이므로, 단순 배경연도를 장식으로 넣은 것인지 점검한다.
   - `구현한 시스템과 맡은 역할, 검증 근거...`는 웹 편집 설명. 삭제하거나 프로젝트 소개에 도움이 되는 자연스러운 문장으로 교체한다.
   - `프로젝트로 확인할 수 있는 역량`도 감정 없는 평가서 표현. 간결한 `기술 역량`을 우선 고려한다.
   - `활동` 및 `연락처` 영역의 독자 안내·행동 유도 문구도 포트폴리오다운 어조로 통일한다.
2. `src/data/meta.js`: `role` / `tagline` / `HomePage.jsx` h1/lede 간 의미 중복 제거. 직무 타이틀은 C++ 응용 SW·시뮬레이션·실시간 통신 축으로 유지하며 백엔드 개발자로 재포지셔닝하지 말 것. 개인 연락처는 기존 값 사용, 이력서에서 집 주소·전화·민감 식별정보를 추가로 옮기지 말 것.
3. `src/data/techStack.js`: 기술 카드에 기술과 실제 증거 프로젝트를 일치시킨다. `Unreal Engine 5`는 GraspLink/RobotPal이 아니라 영묘에서 사용한 기술이므로 연결 표기를 보강할 것. `Google Benchmark`, `Tracy`, `k6` 각각 어디서 사용했는지 실질 사례를 추가할 것. `C++17` 등 사용 버전은 저장소 기준 확인. 자신이 핵심 구현을 하지 않은 팀 기술을 본인 주력 스택으로 보이게 하지 말 것.

## C. 프로젝트별 사실 확정 사항과 상세 수정 명령

### C1. GraspLink — 6축 로봇 시뮬레이션 개인 프로젝트

**핵심 성격:** 로봇 기구학·관절 제한·MoveJ/MoveLinear·충돌 검사·그리퍼·실시간 물리·OpenGL 시연을 직접 개발한 개인 프로젝트. 현재 개발 진행 중.

**반드시 유지·강조할 본인 구현 영역** (소스와 실행으로 확인할 것):
1. HCR-12A 6축 로봇과 2F-85 그리퍼 모델 및 GLB 기준 축/피벗, FK 결과를 화면 렌더링과 Jolt 충돌 형상에 공유.
2. DLS 기반 IK, Jacobian, 관절각 제한, IK 실패 분류/다른 초기값 재시도.
3. MoveJ와 MoveLinear의 동작 차이: 관절 경로 계획(직접 경로 검증 후 제한된 RRT-Connect) vs TCP 직선 표본별 IK(warm start)와 충돌 검사. **MoveLinear가 실패하면 임의로 MoveJ/RRT로 바꾸지 않음.**
4. 고정 제어/물리 업데이트, 다음 목표 자세의 충돌 검사 및 마지막 유효 자세 복원, Jolt 물리와 렌더링 업데이트 주기 경계.
5. 그리퍼 양쪽 접촉 확인과 고정 constraint 기반 파지, Pick-and-Place. 동역학·실제 집기힘이나 하드웨어 제어와 혼동 금지.
6. 시연 중단·재개 및 파지 상태, J6 unwind, 모델 좌표계/피벗 문제 중 **실제 발생한 장애·진단 과정과 코드 증거를 확보할 수 있는 사례**를 우선순위 검토.

**현재 문제/수정 지시:**
- `src/data/projects/grasplink.js`의 `role: 개인 프로젝트로 설계·구현`은 정보를 주지 않음. 개인 프로젝트임을 `team`에 명시하고 역할은 `6축 로봇 기구학·경로 계획·충돌 검사·물리 기반 파지 구현` 등 구체화.
- 첫 문단은 모델명/라이브러리 목록보다 **시뮬레이터가 무엇을 할 수 있는지** 먼저 설명. 예: `6축 로봇팔이 목표 자세로 이동하고 물체를 집어 옮기는 과정을 가상 환경에서 실행하는 C++ 시뮬레이터입니다.` 그 뒤 구현 책임 설명.
- `실제 로봇 하드웨어를 구동하는 제어기는 아닙니다`는 개요 첫 화면의 방어적 끝문장으로 과도함. 실제 실험이 아닌 시뮬레이션인 점은 제목·설명에서 충분히 밝히고, 필요 시 `검증 범위` 한 번만.
- `목표 자세와 TCP 직선 이동 분리`는 핵심 설계/구현이지 **관측된 트러블슈팅**이 아니다. 주요 기능에 유지하고, 문제 해결 사례에서는 실제 버그(예: J6 언와인드, GLB 좌표계/피벗, 경로 제한으로 인한 실패)의 재현→코드 수정→테스트를 우선.
- 현재 `IK 실패가 목표 문제인지 초기값 문제인지 확인`은 결과가 초기값 의존적임을 보여주지만, 코드 변경 과정/테스트 결과가 추상적. `어떤 실패 상태`, `어떤 추가 탐색`, `해 선택/경로 검사`, `실제 결과`를 README/docs/tests에서 추출. 특정 136개 중 38개 값은 특정 입력 사례로만 사용 가능하며 **전체 IK 성공률로 표기 금지**.
- `MoveJ`에서 경로를 먼저 검증하고 안 되면 제한된 RRT-Connect, `MoveLinear`에서는 이전 waypoint의 IK 해를 seed로 재사용, 모두 관절 제한과 충돌 검사. `IK result.path` 등 **IK 해와 계획 경로를 동일시하는 의사코드 금지**.
- `안전 자세 복원`은 실제 코드가 일정 tick의 목표 자세 검사 후 직전 관절각으로 되돌린다는 한정된 의미. **연속 충돌 회피/하드웨어 안전 인증**을 암시하지 않는다. `Idle`과 `Fault`의 실제 전이 정확히 구분.
- 커스텀 physics, friction, torque simulation이라고 암시하지 않는다. Jolt 사용, kinematic body, constraint, 별도 시뮬레이션 한계는 검증 영역에서 명확히.
- `GLB 최대 정점 차이 1.192e-7m`는 모델 자산의 좌표 변환 일치 값이지 로봇 제어 정확도 아님. 메인 성과/홈 카드로 복귀시키지 말 것.
- `64개 중 51개`는 dummy collision callback(항상 통과) 조건이었으므로 collision avoidance 성과로 제시 금지. 필요한 경우 개발자 참고 문서에만 엄격히 한정.
- **시연은 첫 번째 주요 구현 또는 대표 화면 근처**에 두고 클릭 실행. 작동 캡처/GIF가 브라우저 실제 앱과 현재 버전에 일치하는지 확인. 22MB급 legacy asset 등을 페이지 진입만으로 내려받지 않는지 검사.

검증 소스: `cgantro/GraspLink`의 `README.md`, `docs/ROBOT_MOTION_AND_GRASP.md`, `docs/IK_MOVEL_TUTORIAL.md`, `docs/GRIPPER_RUNTIME_DESIGN.md`, `docs/DIAGNOSTICS.md`, 테스트·현재 구현. 파일 문구와 실제 코드가 충돌하면 코드/테스트를 우선하고 모호한 성과는 보류.

**추천 상세 페이지 우선순위:** 개요/시연 → 주요 구현(기구학·경로계획·충돌/물리·파지) → 아키텍처 → 실제 버그 해결 사례 → 검증 범위 → 코드/실행 링크.

### C2. RobotPal — 실장비 보정 + C++ 시뮬레이터 + 카메라 스트리밍

**사용자에게 직접 확인된 사실:** **4인 팀**. Qt GUI, JETANK 실장비 측정과 이동 계수 보정, AGV/로봇팔/그리퍼 제어, Python 모듈 연동, 영상 스트리밍 및 성능 개선은 본인 역할. **공식 프로젝트 기간 표기는 2025.11–2025.12 (월 단위)**. 2026.10 후속 재측정은 별도 표기.

**복원/강조할 영역:**
1. 실물 JETANK 제어·상태 확인 Qt GUI.
2. 모터 입력을 바탕으로 직진 약 **2.4cm/s**, 회전 약 **24°/s** 실측(측정 입력 조건과 적용 단위는 기존 지원서/문서와 대조) → 선속도/각속도 계수 보정. 단순 `실측값 반영`보다 실물 데이터를 어떻게 가상 이동에 연결했는지 설명.
3. 좌/우 모터 입력→AGV 선속도·각속도 변환, 서보 ID→관절·그리퍼·카메라 기능 매핑, Python JSON 제어 명령 수신. 구체 구현의 참조 가능 증거를 확보.
4. OpenGL FBO 카메라 생성 → GPU 픽셀 수집 → JPEG 인코딩 → TCP(Web 환경 WebSocket) 송신. Desktop·WebAssembly 전송 계층 분리 및 Emscripten pthread 실행 조건.
5. PBO 단독 최적화 가설 실패 → Tracy 구간 측정 → JPEG 작업을 주 스레드 critical path 밖으로 분리 → 다시 측정.

**특히 중요한 최신 벤치마크:** `https://github.com/cgantro/RobotPal/blob/main/docs/streaming-performance-result.md` (**Canonical benchmark 2026-10-08**):

| 구성 | 스트리밍 OFF 시뮬 FPS | ON 시뮬 FPS | 송신 FPS | ON으로 인한 감소율 |
|---|---:|---:|---:|---:|
| Sync | 102.38 | 66.70 | 26.95 | 34.84% |
| PBO | 102.52 | 65.60 | 25.49 | 36.02% |
| PBO+4workers | 102.95 | 96.01 | 40.05 | 6.74% |

**홈·대표 성과로는 두 수치만:** `시뮬레이션 ON FPS 66.70→96.01 (+43.9%)`, `카메라 송신 FPS 26.95→40.05 (+48.6%)`; 해상도 1232×832 유지, OFF/ON 각 5회 중앙값, 후속 측정 2026.10. `FPS 감소율 34.84→6.74%`는 부연 수치로 한 곳에만. 송신 목표 60FPS 미달은 정확히 한 번 기재. 구간별 Tracy 수치는 **문제 해결 원인 분석 근거**에 넣지 별도 메인 성과 카드에 넣지 말 것.

Tracy p50: Sync GPU Readback 1.144ms, Sync JPEG 16.406ms, PBO+workers main-thread enqueue 0.017ms, worker JPEG 27.075ms. 개별 JPEG 시간은 오히려 늘었지만 main-thread 대기 분리가 핵심. `JPEG 인코딩 속도 16.406→0.017ms`로 표현하면 **틀린 설명**(다른 연산 구간의 측정값). PBO-only는 ON 65.60, 송신 25.49로 baseline보다 개선되지 않음. **PBO가 언제나 느리다는 보편 결론 금지.**

**보강/수정:**
- 현재 `results`가 `architecture`보다 먼저 나오지만, **실장비 보정·AGV 제어 역할은 첫 화면에서 묻히면 안 됨**. `role`을 일괄 나열하기보다 개인 구현 그룹으로 짧게 분리.
- 현재 실제 `robotpal.js`의 성능 측정 표(`performanceRows`)는 `동기`와 `PBO+작업스레드` 칼럼에 값이 한쪽만 표시되는 4행 표여서 눈으로 비교하기 어렵고, 다른 연산 구간의 값이 전후 비교로 오해될 수 있음. 스트리밍 처리 흐름 그림 + 각 단계 p50 표 또는 baseline/after 명확히 구분한 소표를 쓰도록 개선.
- 구조 설명은 시뮬레이터 제어와 영상 전송 두 흐름을 분리해서 보여준다: `Python 명령→네트워크→AGV/로봇팔 제어`와 `OpenGL 카메라→Readback→JPEG→전송`. 전체 시스템 아키텍처에서 팀의 공통 엔진 작업을 내 역할로 오인하지 않도록 표시.
- `실장비 측정·보정`은 실제 기능 구현 과정으로 적합. 보정 전후 오차나 반복 시험 통계가 없으면 **개선 오차 수치를 만들어내지 않고** 측정값 적용 사실까지만 적는다.
- 성능 트러블슈팅의 `상황`은 `실제 스트리밍 시 Simulation FPS 하락`; `원인 확인`은 `PBO-only 실패와 Tracy로 JPEG 16.406ms vs Readback 1.144ms`; `변경`은 `PBO + 4worker, 주 스레드 큐 등록 후 진행`; `결과`는 두 FPS. 이 내용을 6칸 × 중복 카드에서 **하나의 선명한 엔지니어링 사례**로 재구성.
- **Qt 구현이 현재 공개 RobotPal 저장소에 없다면** 사용자가 확인한 실제 본인 역할로 표기하되, 공개 저장소에서 재현 가능한 기능인 것처럼 코드 출처를 꾸며내지 않는다. 추가 증빙 링크를 찾을 수 있으면 사용한다.
- 사용 기술 `libjpeg-turbo`가 최신 canonical benchmark의 실제 인코더 구현과 일치하는지 원본 코드 확인. 기준 보고서에는 `stb_image_write`에 대한 분석도 포함되어 있어 인코더 종류와 버전을 섞어 서술하지 말 것.
- 2025년 프로젝트 당시 수치 `32.9→37.3fps` 등 **오래된 탐색 측정**은 2026.10 canonical과 절대 한 프로젝트 성과에서 혼합하지 않는다.

**추천 페이지:** 개요/개인 역할/실물 보정 → 스트리밍 성과 두 지표 → 시스템 처리 흐름 → 문제 해결(PBO 실패/Tracy/병렬화) → 측정 조건 → 소스 링크.

### C3. 영묘 (Mausoleum) — UE5 멀티 룸/음성/게임 서버

**실제 본인 역할, 사용자의 기존 지원서와 소스로 입증된 범위:**
- C++ WebSocket 로비 서버, 방 생성/입장/퇴장/호스트 변경/세션 동기화.
- UE Dedicated Server 기반 다중 게임 세션과 RoomCode 매핑, 방별 게임 진행 페이즈·아이템 스폰(실제 코드에서 담당 클래스 확인).
- C++ UDP 음성 서버, RoomCode에 의한 음성 분배/작업자 샤딩, UDP 패킷 검증, 브로드캐스트.
- UE5 클라이언트 음성 캡처·Opus 인코딩/디코딩·재생, 화자별 코덱 상태, 포커스 복귀 버퍼 초기화. 생사 분리 전략 패턴이 직접 구현 역할인지 원래 제출 문서/실제 소스에서 확인 후 보강.
- 플랫폼 소켓 이벤트 루프 `epoll/select` 분리(실제 파일에서 확인).

**현재 문제/지시:**
- `src/data/projects/mausoleum.js`는 주요 구현 4개를 나열하지만 프로젝트 개요가 음성 기능 중심으로 써 있어 **게임/로비/다중 서버/룸 분리의 중요도가 축소**됨. 로비·게임 DS·음성 서버라는 독립 책임을 한 눈에 보이는 시스템 아키텍처로 제시.
- 대표 `약 90.3% Opus 음성 페이로드 감소`는 16-bit PCM vs Opus 애플리케이션 페이로드의 **형식/설정 관련 크기 비교**임. `총 네트워크 대역폭 90.3% 절감`, `실측 지연 개선`, `패킷 복구 성능 향상`으로 확대 금지. 메인 첫 화면을 이 수치로 지배하지 않게 조정. `16kHz/20ms/24kbps`는 성과가 아니라 음성 인코딩 설정.
- **검증된 트러블슈팅 1:** 포커스 복귀 시 쌓인 오래된 음성. 오디오 캡처 경계와 PCM 링 버퍼/코덱 상태를 구분해서 실제 현상, 처리 조건, 수정 결과 작성.
- **검증된 설계 선택/사례 2:** RoomCode 해시 샤딩과 큐 분리. *실측 병목이 발생한 것처럼 쓰지 말 것*. 설계 요구(룸별 순서 보존/다중 룸 격리) → 샤드 분배 → 구현. 사후 처리량/지연 개선량은 계측 미확인.
- 기존 이력서에 기록된 다중 세션 상태 혼선 방지(RoomCode 공통 식별자, 게임 상태·페이즈·음성·공간 오프셋) 사례를 중요한 설계 결정으로 검토. 실제 적용 여부를 소스에서 확인할 것.
- **심각한 누락:** `links.github: null`이나 `cgantro/Mausoleum` 저장소는 **public**임을 확인했음. 정확한 저장소 URL(`https://github.com/cgantro/Mausoleum`) 연결. 공개 가능한 실행 영상/데모가 없으면 만들지 말 것.
- 기존 `code`의 `ProcessCapture()` 발췌는 중간의 `// 정상 캡처 처리`를 직접 만든 **축약 코드**로서 완전한 실제 소스 발췌라고 표기하면 안 됨. 실제 소스와 동일한 연속 구간을 선택해 `원본 코드 일부 발췌`라고 표시하거나, 일부 삭제/변형됐으면 `핵심 로직을 단순화한 예시`라고 명시(가능하면 실제 코드 우선).
- 원본 실제 경로: `cgantro/Mausoleum/A302/Source/A302Client/Voice/Capture/VoiceCaptureProcessor.cpp`. 처리:
  - `!FApp::HasFocus()` → `DrainAllCaptureData()` → `ResetCodecForRealtime()` → return.
  - `AvailableData > 8192B` → 전체 폐기 + reset.
  - `4096B < AvailableData <= 8192B` → 오래된 초과분만 drain하고 최대 4096B 읽기.
  - 코덱 `Encode`는 내부 링 버퍼에 PCM을 모아 16kHz mono 16bit 20ms **640B 프레임 단위**로 Opus 인코딩. `4096B`를 **Opus 프레임 크기로 설명하지 말 것**.
- 코드의 주석은 실제 코드보다 장황하지 않게, 핵심 분기 이유만 설명. 클래스/컴포넌트가 `UPrivateVoiceChatComponent`, `UVoiceCaptureProcessor`, `UVoiceCodec` 중 어느 책임을 맡는지 정확히 구분.
- `HRTF` 기술 태그가 실제로 사용자 구현인지/현재 코드 경로인지 검증. 기술 명칭 나열을 위한 태그는 제거.

**추천 페이지:** 개요/본인 서버 영역 → 로비·UE DS·음성 서버 아키텍처 → 주요 구현 → 포커스 복귀 실제 트러블슈팅 + 다중 룸 샤딩 설계 → 범위를 명시한 Opus 전송 크기 → 공개 GitHub 링크.

### C4. AutowingCar — 공항 이동체 관제 백엔드

**포지셔닝:** 메인 직무의 C++ 프로젝트와 달리 Java/Spring Boot 프로젝트이지만, **실시간 통신/상태 정합성/경로 계획**이라는 직접 관련된 개발 능력 때문에 대표 프로젝트로 유지. `보조 사례`, `C++ 기술을 증명하는 예시` 같은 자기해설 문장 사용 금지.

**본인 핵심 구현 영역 — 현재 `implementations` 2개는 심각한 축약:**
1. MQTT 상태 수신·파싱, 차량 monitoring·명령·ACK, STOMP/WebSocket 채널 별 갱신. 명령 발행과 장비 보고 상태의 확정 기준 분리.
2. 상태 FSM, 중복/역행 보호, 자동 액션의 상태 우선순위, `DOCKING`/`MOVING_TO_GATE` payload 역행 방어.
3. `TxUtil.executeAfterCommit` 커밋 후 MQTT/WebSocket 이벤트 발행. **정합성 경계**와 한계(커밋 후 발행 전 프로세스 종료, 아웃박스/재시도 미구현) 정확히.
4. 공항 지도 그래프 경로 탐색(`A*` + `Yen K=3` 대안 경로, 사용 중/통제 노드·간선 제외), `RDP` 경유지 단순화; 실제 구현 확인 후 명시. 현재 대표 화면에서 실질적인 경로 탐색 능력이 묻히지 않게.
5. Redis 최신 상태, PostgreSQL 영속 처리와 DB 상태 저장 흐름. `DrivingLog` 처리 방식도 과장 없이 기술(실제 구현 구조 검증).
6. k6 500개 모의 차량 클라이언트 ×10Hz 부하 검증. 수치 `최대 8,935 msg/s`, `E2E 14–28ms`의 **통계 기준 불명**. 데이터 출처, 단위, 이벤트 측정 경계가 확인되면 제시하고, 확인 안 되면 `기록된 최대 처리량`으로 한정하며 이를 단정적인 보장 성능처럼 홍보하지 말 것. 500×10Hz=기본 5000msg/s와 순간 8935msg/s의 관계(양방향 합산/순간 최대 등)는 모르면 추정해서 설명하지 말 것.
7. JWT/SOCKET 인증·CI/CD·API 예외처리 등 본인이 수행한 추가 업무는 **부가 구현**으로 1~2줄 언급 가능하지만 C++ 실시간 직무와 직접 연결되는 내용보다 앞에 배치하지 않는다.

**트러블슈팅은 독립적으로 2개:**
- 상태 롤백: 자동 액션으로 `DOCKING` 상태가 된 다음, 오래된 monitoring 상태 `MOVING_TO_GATE`가 덮어씀. **실제 코드**: `assignedCar.getCarStatus() == DOCKING && status == MOVING_TO_GATE` 방어, `preAutoActionStatus`를 저장하고 `checkAndTriggerAutoActions(...)` 전후 상태 비교. 실제 발생한 입력 순서/관측 현상을 가능한 한 확인하고 정확히 씀. `stateChanged` 등 코드에 없는 임의 API를 도입하지 않는다.
- 커밋 전 발행: 트랜잭션 안에서 외부 메시지가 DB 커밋보다 먼저 전송됨. `TxUtil.executeAfterCommit`로 DB commit 뒤 발행. DB와 MQ 원자적 전달·exactly-once를 보장했다고 하면 틀림. 코드 조각은 실제 경로/호출부에서 정확히 발췌.
- `A* / Yen / 우회 정책`은 업무 기능/의사결정 사례, 실제 경로 실패를 재현한 사례가 없으면 무조건 트러블슈팅으로 만들지 않는다.
- 부하 시험은 검증 구간. 사례에 별도의 실제 부하 병목 수정이 없는 한 문제 해결을 꾸미지 말 것.

**다른 팀의 AI 수신호 인식, ArUco 도킹, STM32 모터 제어, ROS2**는 시스템 개요/아키텍처 전체 경로에는 등장할 수 있지만, **본인 담당 섹션·기술 스택·성과**에 넣지 않는다.

증거 자료: `cgantro/Portfolio/data/projects/agv.md`의 `내 구현`, 상태 로직, 알고리즘, 성능 절. GitLab 등 원본 코드를 실제로 접근할 수 있으면 비교; 접근 불가하면 포트폴리오 내부 기록과 사용자 지원서 범위를 넘어 상세 API 구현을 새로 지어내지 말 것. AutowingCar 공개 저장소 주소가 불명확하면 링크를 만들지 않는다.

**추천 페이지:** 개요/백엔드 전담 역할 → MQTT/상태 흐름 아키텍처 → 주요 기능(상태·통신·경로·저장) → 실제 2개 문제 해결 → k6 측정 조건 → 공개 가능한 자료.

## D. 실제 코드·의사코드 작성의 절대 규칙

1. **기본값: 코드 없음.** 중요한 오해가 없어야 할 분기·동시성 처리·연산이 있고 실제 코드가 이를 보여줄 때만 사용.
2. `실제 구현 발췌`는 원본 파일의 실제 연속 구간과 비교 가능해야 한다. 핵심 구간만 발췌하면 코드 블록 바로 위에 파일명/경로를 링크한다. `...`나 `// 정상 처리`로 생략하면 `일부 생략`을 명시하고 **직접 코드인 척하지 말 것**.
3. **의사코드가 꼭 필요하면** 변수·조건·반환값의 책임과 자료형이 의미상 맞아야 한다. 설계/분석 과정의 사람 판단을 JS식 `if (fpsBad) rewriteArchitecture()` 형태의 가짜 런타임 코드로 표현하지 않는다.
4. 주석은 왜 이 조건이 필요한지 설명하는 한두 줄. 코드 모든 줄에 번역 주석 금지. 이름이 설명하는 코드를 주석으로 그대로 반복하지 말 것.
5. `한 파일당 코드 하나` 같은 인위적 규칙 없음. 문제 해결에 필요하면 2개도 가능, 불필요하면 없음. 코드 블록 위·아래의 문단이 코드 의미를 설명하고 중복하지 않도록 편집.
6. 기능 구현 근거를 보여줄 **그림 vs 코드 vs 데이터 표 중 한 가지를 우선 선택**. 같은 이야기를 4단계 플로우·의사코드·문단·수치 카드로 4번 반복하지 않는다.
7. 예시 배치: GraspLink의 실제 IK–관절경로 분기, Mausoleum의 `ProcessCapture` 포커스/백로그 경계, AutowingCar의 상태 역행 방어 또는 afterCommit. RobotPal 병목 사례는 소스 코드보다 Tracy 측정 표/병목 이동 흐름이 적절할 수 있다.
8. 함수/클래스 명칭은 원본 소스의 대소문자와 네임스페이스가 정확해야 한다. 실제 레포 주소를 제공하되 링크가 열리는지 확인.
9. 코드 복사 버튼·줄 번호는 실제 이용 가치가 있을 때만. 기본 들여쓰기 유지, 수평 스크롤, 최소 12~13px 이상 가독성, 모바일 대응.
10. 빌드되는 코드인지 여부와 관계없이 **코드 의미가 실제 구현과 달라지면 실패**. 샘플 실행 가능성을 꾸며내지 말 것.

## E. 트러블슈팅의 편집 테스트

각 사례를 다음 7개 질문으로 검토하고, 하나라도 비어 있으면 추상적인 표현을 보강하거나 사례를 `설계 선택`으로 이동한다.

1. 실제로 무엇이 잘못 보였는가? (현상 또는 계측 차이)
2. 어떤 조건에서 재현되었는가? (가능한 범위, 숫자는 없으면 생략)
3. 처음 생각한 원인은 무엇이었나? 실제 가설이 있었을 때만.
4. 어떤 로그, 프로파일링, 코드 흐름으로 원인을 좁혔나?
5. 어떤 코드/설계가 어떻게 바뀌었나?
6. 무엇이 달라졌는가? (테스트, 비교 수치, 현상 재발 유무 — 확보 범위만)
7. 남은 한계는 채용 담당자의 기술적 판단에 중요한가? 중요하면 한 번만, 중요하지 않으면 개인 개발 기록으로 이동.

**허용되는 사례 유형:** 성능 병목 분석, 버퍼 누적 해결, 상태 롤백 방어, 커밋/이벤트 순서 수정, 경로 계획 예외 처리 등. **별도 영역으로 구분해야 하는 유형:** 아키텍처 원칙, 기능 선택 이유, 검증용 수치, 기능 설명 자체.

예시 — RobotPal의 자연스러운 사례 문체:

> 카메라 스트리밍을 켜면 시뮬레이션 FPS가 떨어졌습니다. 처음에는 GPU에서 픽셀을 읽는 과정이 원인이라고 보고 PBO를 적용했지만, 단독 적용만으로는 성능이 개선되지 않았습니다. Tracy로 처리 구간을 나눠 측정하자 동기 방식에서 픽셀 읽기는 p50 1.144ms, JPEG 인코딩은 16.406ms가 걸렸습니다. JPEG 작업을 별도 스레드로 분리하고 주 스레드는 작업 큐에 프레임을 등록한 뒤 다음 시뮬레이션 작업을 진행하도록 바꿨습니다. 2026년 10월 동일 조건의 후속 측정에서 스트리밍 중 시뮬레이션 FPS는 66.70에서 96.01로, 카메라 송신 FPS는 26.95에서 40.05로 증가했습니다.

위 예문은 **문장 구조의 예시**이며 측정 시점, 5회 중앙값 조건, 목표 미달 사실을 빠뜨리지 않도록 별도 측정 각주/표에 남긴다. 한 문단이 너무 길면 2문단으로 나눈다.

예시 — AutowingCar (실제 상태 문제와 해결 코드):

> 게이트 도착 후 자동 처리로 차량 상태가 `DOCKING`으로 전환됐는데, 이전 위치 메시지에 담긴 `MOVING_TO_GATE` 값이 나중에 반영되면서 상태가 되돌아가는 문제가 있었습니다. 이미 도킹 상태라면 이전 이동 상태를 무시하고, 자동 액션 실행 전후 상태를 비교해 서버가 전환한 상태를 우선 저장하도록 수정했습니다.

예시 — 영묘 (상황과 복귀 동작):

> 게임 창이 비활성화된 뒤 복귀하면 오래된 음성 데이터가 한꺼번에 처리돼 소리가 끊기는 문제가 있었습니다. 포커스가 없을 때 캡처 버퍼를 비우고 Opus 코덱을 초기화했으며, 누적 데이터가 일정 크기를 넘으면 이전 데이터를 폐기하도록 했습니다. 음성 데이터를 밀린 순서대로 모두 전달하기보다 현재 음성부터 재개하는 방식으로 처리했습니다.

## F. 디자인·UX·표시·접근성 검수

1. **첫 화면:** C++ 개발자 포지션, 실제 프로젝트 목록, 기술적 차별점이 바로 보이는가. 같은 단어의 반복(`C++`, `실시간`, `구현`)이 영웅 영역 전체를 채우지 않는가.
2. **홈 프로젝트 카드:** 이미지 → 프로젝트 한 문장 개요 → **내 역할 한 줄** → 핵심 증거/강점 → 관련 기술 3~5개. 기술 태그/하이라이트 중복을 없앤다. 네 개 프로젝트 카드의 설명 길이·줄바꿈 균형을 확인.
3. **본문:** 본문 12px 미만으로 과도한 압축을 하지 않는다. 긴 서술은 넓은 2열 `dl`보다 가독성 좋은 1열 콘텐츠로 정리. 줄 길이/행간/문단 간격을 실제 한글 문장 길이에 맞춘다.
4. **표:** 측정 집단/단위/p50/조건 헤더 명확히. 가로 스크롤 가능한 모바일 표와 접근 가능한 `<caption>` 제공. `—`가 과다한 희소 비교 표는 구조를 재설계.
5. **시연:** GraspLink 데모 클릭 시 지연 로드, 실패 시 일반 GitHub/새 창 링크, 미지원 브라우저용 안내. WebAssembly/COOP·COEP와 iframe 로딩 기능 점검. GIF는 loading 전략과 파일 크기 확인. 페이지 진입만으로 대형 WASM/기타 전체 데모가 자동 로드되지 않게.
6. **앵커/라우팅:** 홈/상세의 `/`, `/#projects` 복귀 시 실제 스크롤 및 활성 메뉴 동작 확인. Page route 이동 시 이전 페이지의 scrollY가 유지되어 프로젝트 상세가 중간부터 열리지 않는지 확인.
7. **링크:** 공개 repo가 있는 영묘의 `links.github` 복원, 없는 AutowingCar 주소 임의 생성 금지. GitHub README 링크/데모 base path `/Portfolio/` 일치.
8. **접근성:** 이미지 alt가 이미지를 이해하도록 구체적, 데모 iframe 제목, heading h1/h2/h3 계층, 버튼 focus, 키보드 이동, 축소 화면 대비/명도, anchor 위치를 확인.
9. **복사/인코딩:** `%)1232`처럼 텍스트가 붙어 복사되는 현상, HTML entity 문자열(`&#x...;`)의 실제 DOM 노출 여부를 브라우저에서 확인. HTML 소스나 ChatGPT 복사 변환과 사이트 원본 문제를 구분하고, 실제 DOM에 문제가 확인된 것만 고친다.
10. **증거 자료 연결:** 아키텍처 이미지가 실제 현재 구조인지, 시연 이미지가 프로젝트 자체를 정확히 대표하는지 검토. 임의 AI 생성 아키텍처를 기술 근거로 사용하지 않음.
