# RobotPal

## 프로젝트 개요

실물 JETANK의 주행과 로봇 팔 조작을 가상 환경에서 시험하는 시뮬레이터입니다. 가상 카메라와 Python 영상 인식 모듈을 연결해 인식 결과를 가상·실물 장비의 제어에 사용합니다. 개발 기간은 2025년 11~12월이며 4인 팀으로 진행했고, C++17·OpenGL·JPEG·Tracy를 사용했습니다.

## 주요 기능

- 가상 JETANK을 주행시키고 로봇 팔과 집게를 조작합니다.
- 가상 카메라 영상을 Python 영상 인식 모듈로 보내고, 인식 결과를 이동체·로봇 팔·집게 명령으로 연결합니다.
- 실물 JETANK의 상태를 확인하고 주행 명령을 보냅니다.
- 실물 JETANK에서 측정한 주행값을 가상 이동 속도에 반영합니다.
- 카메라 영상을 JPEG로 압축해 TCP로 전송합니다.

## 담당 역할

카메라 영상 전송과 제어·실물 장비 연동을 맡았습니다. 실물 JETANK의 주행값을 측정해 가상 이동 속도를 맞추고, Python 인식 명령을 이동체·로봇 팔·집게 조작에 연결했습니다. 성능 분석에서는 Tracy로 JPEG 압축이 메인 스레드를 오래 점유하는 지점을 확인했습니다.

## 트러블슈팅

### JPEG 압축 때문에 스트리밍 중 시뮬레이션이 느려짐

스트리밍을 켜자 시뮬레이션 갱신률이 102.38 FPS에서 66.70 FPS로 떨어졌습니다. GPU Readback을 병목으로 보고 PBO를 적용했지만 65.60 FPS에 그쳤습니다. Tracy에서 동기 Readback p50은 1.144ms, 메인 스레드 JPEG 압축 p50은 16.406ms여서 JPEG 압축을 먼저 분리하기로 했습니다.

프레임을 인코딩 대기열에 넣는 시간은 메인 스레드 p50 0.017ms였고, 워커에서 JPEG 한 건을 압축하는 시간은 p50 27.075ms였습니다. 개별 압축 시간은 늘었지만 메인 스레드가 압축이 끝날 때까지 기다리지 않아 시뮬레이션 계산을 이어갈 수 있었습니다.

JPEG 압축 작업 대기열은 최대 6프레임을 보관하고 가득 차면 가장 오래된 프레임을 버립니다. 압축이 끝난 프레임은 별도의 TCP 송신 대기열로 넘기며, 이 대기열은 최대 2프레임만 보관합니다. 압축 워커의 완료 순서가 바뀌어 오래된 프레임이 늦게 도착하면 프레임 번호를 확인해 보내지 않습니다.

```cpp title="RobotPal/src/Util/StreamingWorker.cpp · JPEG 인코딩 대기열"

    std::lock_guard<std::mutex> lk(m_encodeQueueMutex);
    if (m_encodeQueue.size() >= EncodeQueueCapacity)
        m_encodeQueue.pop();
    m_encodeQueue.push(std::move(job));

m_encodeQueueCv.notify_one();
```

| 구성 | 스트리밍 중 시뮬레이션 | 카메라 송신률 | 갱신률 저하 |
| --- | ---: | ---: | ---: |
| 동기 Readback·JPEG | 66.70 FPS | 26.95 FPS | 34.84% |
| PBO·JPEG | 65.60 FPS | 25.49 FPS | 36.02% |
| PBO·JPEG 워커 4개 | 96.01 FPS | 40.05 FPS | 6.74% |

표의 값은 1232×832 해상도에서 각 구성을 5회 실행한 중앙값입니다. 2026년 10월 8일 공개 측정 기록이며, 수신과 압축 해제는 측정에 포함하지 않았습니다.

## 결과

동기 Readback·JPEG 구성과 비교해 워커 4개 구성에서 스트리밍 중 시뮬레이션 갱신률은 66.70→96.01 FPS, 카메라 송신률은 26.95→40.05 FPS로 높아졌습니다. 스트리밍에 따른 시뮬레이션 갱신률 저하도 34.84%에서 6.74%로 줄었습니다. 송신률은 목표 60 FPS에 도달하지 못했습니다.

측정은 1232×832 해상도에서 스트리밍을 끄고 켠 상태를 각각 5회 실행한 중앙값이며, 영상 수신과 압축 해제는 제외했습니다. 정확한 하드웨어 모델과 원본 로그는 공개 기록에 없습니다.
