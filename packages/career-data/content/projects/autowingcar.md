# 오토잉카 (AutoWing Car)

## 개요

공항 토잉카 관제 서버를 만드는 6인 팀 프로젝트에서 서버 전반을 맡았습니다. 차량 장치의 명령·상태 통신부터 경로 계획, 데이터 저장, 관제 화면 갱신까지 연결했습니다.

## 구현

### 차량 통신과 관제 화면

차량 장치와 MQTT로 명령을 주고받고, 위치·속도·배터리·운행 상태와 명령 수신 확인을 처리했습니다. 서버가 보낸 명령 상태와 차량이 보고한 실제 주행 상태는 별도로 관리해 명령을 전달했다는 이유만으로 차량이 움직인 것처럼 저장되지 않게 했습니다.

관제 화면은 WebSocket과 STOMP로 연결했습니다. 차량, 항공편, 비상 알림에서 바뀐 정보만 전달해 화면을 갱신하고, 차량의 위치와 상태는 주행 이력에 기록했습니다.

### 경로 계획

A*로 기본 경로를 찾을 때 통제 구간이나 다른 차량이 점유한 연결선은 제외했습니다. 연결선의 예상 이동 시간을 비용으로 사용하고 값이 없으면 거리 나누기 10으로 보정했습니다. 목적지까지의 예상 비용은 직선 거리와 최고 속도로 계산합니다.

기본 경로 외에 Yen 알고리즘으로 우회 경로를 최대 세 개까지 구했습니다. 차량에 보낼 때는 Ramer–Douglas–Peucker 방식으로 경로 모양에 영향이 적은 점을 줄이고, 허용 오차를 넘는 꺾임은 남겼습니다.

### 저장과 배포

PostgreSQL에는 지도와 주행 이력을 저장하고, 개발·시험에는 H2를 사용했습니다. Redis는 최신 차량 상태와 만료 시간을 관리하는 로그인 갱신 토큰에 사용했습니다. JWT 요청 확인, Docker 실행 환경, GitLab CI 빌드·배포도 구성했습니다.

## 문제 해결 과정

차량이 출입구에 도착하면 서버가 상태를 ‘도킹 완료’로 바꿨지만, 같은 주기에 처리한 차량 메시지가 이전 상태인 ‘출입구로 이동 중’을 다시 저장해 도착 처리가 반복됐습니다. 수신 상태를 바로 저장하지 않고 기존 데이터베이스 상태와 비교하도록 바꿨습니다. 자동 처리로 상태가 바뀌었다면 새 상태를 유지하고, 바뀌지 않았다면 차량 상태를 저장합니다.

또한 데이터베이스 저장 중 차량에 명령을 먼저 보내면 저장이 취소돼도 장비가 명령을 받을 수 있었습니다. 명령 전송을 트랜잭션 확정 뒤로 옮겨 데이터 저장과 장비 동작 순서를 맞췄습니다.
